## (1) Delete zombie Failed renovate Jobs

**Context**: Three pre-fix Failed Job objects (`renovate-29726280-…-400`,
`renovate-29726280-…-520`) keep re-firing `KubeJobFailed` because
`failedJobsHistoryLimit: 3` preserves them and the CronJob's `concurrencyPolicy:
Forbid` prevents new runs from cleaning up old ones. The actual renovate CronJob is
healthy — these are artifacts of the 2026-07-08/09 OOM cycle before
`concurrentRequestLimit=2` and the 6Gi limit landed.

**Commands** (on `pve-mgmt-01` or any node with kubectl access):

```bash
# List them to confirm
kubectl get jobs -n apps --sort-by=.metadata.creationTimestamp | grep renovate

# Delete the three zombie jobs + their pods
kubectl delete job -n apps renovate-29726280-…-400
kubectl delete job -n apps renovate-29726280-…-520
kubectl delete job -n apps renovate-29726280-…-???   # fill in the third

# Confirm they're gone
kubectl get jobs -n apps --sort-by=.metadata.creationTimestamp | grep renovate
```

**Verify alert stops**: Check Discord 4h later (alertmanager `repeat_interval`
for `KubeJobFailed` is 4h). The `KubeJobFailed` alert matches on
`kube_job_status_failed > 0` — once no Failed Jobs exist, no series fires.

**Note**: The CronJob's `failedJobsHistoryLimit: 3` means new failures will
repopulate up to 3 — but with the OOM fix in place (6Gi limit + `concurrentRequestLimit=2`),
new failures shouldn't appear. If they do, the root cause is not the old jobs.

## (2) Verify daily-backup ran clean

**Schedule**: `daily-backup` runs at `05:00 UTC` daily (`kubernetes/system/velero/schedule.yml`).

**Commands**:

```bash
# List the last few backups
velero backup get --sort-by=.metadata.creationTimestamp | tail -5

# Check the most recent one for failures
velero backup describe <latest-daily-backup-name> --details | grep -E "Phase|Warnings|Errors"

# Confirm PVC data was captured (not just manifests)
velero backup describe <latest-daily-backup-name> --details | grep -E "PodVolumeBackup|ResticRepository"
```

**What "clean" looks like**:

- `Phase: Completed` (not `PartialFailure` or `Failed`)
- `Warnings: 0` (or only expected non-actionable ones)
- `Errors: 0`
- PodVolumeBackup entries present for PVCs (Postgres, Vaultwarden, etc.)

**Also verify native CNPG backup**:

```bash
kubectl get backups -n database --sort-by=.metadata.creationTimestamp | tail -3
```

If both Velero and CNPG backups succeeded, the repos are backed up.

## (3) Propose #378 small-batch re-enable plan

**What #378 is**: `system-app-bootstrap` — an ArgoCD Application that
auto-discovers all `kubernetes/system/*/application.yml` and
`kubernetes/system/*/manifests-application.yml` files via recursive glob.
Closes the orphaned-bootstrap-file trap class (18 of 41 Applications
had their defining file untracked by any parent).

**Status**: Committed to `main` (commit `d6602c9`) but deliberately not wired
into any active Application — the file exists but nothing watches it.

### Re-enable plan (small-batch, staged)

**Goal**: Reconcile the 18 previously-orphaned files without one big bang.
Each stage adds a subset, verifies clean sync, then proceeds.

#### Pre-conditions

- [ ] `velero backup get` shows a recent clean backup (so rollback = Velero restore)
- [ ] `kubectl get applications -n argocd` — all `Synced`/`Healthy`

#### Stage 1: Wire system-app-bootstrap into argocd-manifests (low risk)

The "go" step: add `system-app-bootstrap` to argocd-manifests' include list.

```bash
# In git, edit kubernetes/system/argocd/manifests-application.yml:
# Add "system-app-bootstrap" to the directory.include list:
#   '{ingressroute,external-secret,argocd-notifications-cm,
#     notifications-external-secret,network-policies,system-app-bootstrap}.yml'
#
# Commit + push → Atlantis PR → merge
```

**What this does**: ArgoCD picks up the new include, starts watching
`kubernetes/system/argocd/system-app-bootstrap.yml`, which triggers the
first recursive sync of `kubernetes/system/*/application.yml`.

**Risk**: First sync reconciles ~15 previously-orphaned files. Most should
already match live (they were created via `kubectl apply` and not
hand-edited since), but this needs explicit verification.

**Rollback**: Remove `system-app-bootstrap` from the include list.
ArgoCD stops watching it. The ~15 files it reconciled stay in their
current state (they're now live, but no selfHeal on them from this path).

#### Stage 2: Verify the first-sync drift (medium risk)

After Stage 1 merges:

```bash
# Check for any unexpected drift
kubectl get applications -n argocd | grep -v Synced
kubectl get applications -n argocd | grep -v Healthy

# Diff each newly-reconciled Application against what was live before
# (kubectl get -o yaml on a few and compare to git)
```

**Gate**: No unsynced/unhealthy Applications → proceed.
If drift found: fix in git (not `kubectl apply`), let ArgoCD reconcile.

#### Stage 3: Enable selfHeal on the bootstrap file itself

Once Stage 2 is clean, add `selfHeal: true` to system-app-bootstrap's
Application spec. This means future git drift auto-corrects.

**Risk**: Same as any selfHeal — if git and live drift unintentionally,
ArgoCD overwrites live with git. The deliberate exclusion of ArgoCD's own
core config files (argocd-cm.yml etc.) from the glob pattern mitigates
the worst blast-radius scenario.

**Rollback**: Set `selfHeal: false` on the Application, or remove the
include from argocd-manifests entirely.

#### Timeline

- **This maintenance window**: Stage 1 (wire the include) + Stage 2 (verify)
- **Next day**: Stage 3 (enable selfHeal) — after confirming Stage 1 didn't
  surface anything unexpected
- **Ongoing**: New Applications under `kubernetes/system/` are auto-discovered;
  the orphaned-file trap class is closed permanently

#### What stays excluded (by design)

ArgoCD's own bootstrap files (`argocd-cm.yml`, `argocd-cmd-params-cm.yml`,
`argocd-rbac-cm.yml`, `apps-applicationset.yaml`) remain outside the glob
pattern. selfHeal on these has cluster-wide blast radius — same reasoning
as `argocd-manifests.yml`'s own header comment. They stay in the "manual
apply" bucket permanently.
