# ADR-050: Remove Scrutiny — its collector cannot see the disks it was meant to watch

- **Status**: Accepted and applied, 2026-10-03
- **Relates to**: ADR-027 (monitoring drift), `docs/HARDWARE.md` (single-host
  constraint, NVMe wear thresholds), `docs/STEADY-STATE.md` (`fwd_04a_srv_monitoring`)

## Context

Scrutiny was deployed on 2026-07-20 as a hub/spoke S.M.A.R.T. stack: an InfluxDB
StatefulSet, a `scrutiny-web` Deployment, and a `scrutiny-collector` DaemonSet on
all three k3s nodes, fronted by an Authelia-gated IngressRoute. The collector was
given `hostPID: true`, `CAP_SYS_RAWIO` and a writable `/dev` hostPath specifically
so that `smartctl` could read host disks.

It has never once worked. Checking it on 2026-10-02, because the InfluxDB buckets
had shown up empty during the InfluxDB digest upgrade in
[PR #815](https://github.com/dwoitzik/homelab-infrastructure/pull/815):

```console
$ kubectl -n apps exec scrutiny-influxdb-0 -- influx bucket list
  scrutiny           a1564ff8bc47951a  Shards=0
  scrutiny_weekly    91bf573067a36422  Shards=0
  scrutiny_monthly   0e5f21fdcfbebd3b  Shards=0
  scrutiny_yearly    88f5067b56985eeb  Shards=0
```

Zero shards, meaning no series were ever written. There is no `scrutiny.db` either,
so no device was ever registered. The web log contains only `kube-probe` health
checks — not a single `POST` from a collector, in the whole retention window.

## The two independent reasons

**1. The collector cannot open the VMs' disks.** Running the collector by hand:

```console
Executing command: smartctl --scan --json
  /dev/sda -d scsi
Executing command: smartctl --info --json /dev/sda
  Smartctl open device: /dev/sda failed: Operation not permitted
  Could not retrieve device information for sda: exit status 2
```

Not a capability problem — `CAP_SYS_RAWIO` *is* granted (bit 17 of
`CapEff=0x00000000a80625fb`), and `kubectl exec` already runs as uid 0. A plain
`dd if=/dev/sda` fails the same way. This is the device cgroup: K3s runs cgroup v2,
where device access is an eBPF allowlist the runtime builds from what was actually
passed into the container. Mounting `/dev` as a hostPath directory puts the device
nodes *in the namespace* but does not put them *on the allowlist*. Upstream's own
guidance for the identical failure is `--device-cgroup-rule='c *:* rwm'`, and the
Kubernetes API has no equivalent field. The only thing that would work is
`privileged: true`.

**2. Even privileged, it would be watching the wrong disk.** This is the part that
makes the fix wrong rather than just difficult. Per `docs/HARDWARE.md`,
`pve-mgmt-01` is the sole physical node and the three `vm-srv-k3s-*` hosts are VMs
whose boot disks are LVM-thin volumes carved out of that node's NVMe. A collector
inside a guest can never see `/dev/nvme0n1` on `pve-mgmt-01` — the disk whose
failure takes down everything, and the one `HARDWARE.md` warns about at 56% wear
with `media_errors > 0`. SMART readings from a virtio guest describe a virtual
disk and would tell us nothing about the hardware. So `privileged: true` would
grant a broad privilege escalation across the whole cluster to obtain data of no
value.

## Why not fix it

The capability this stack exists to provide is already implemented, on the host,
where it is actually meaningful: `ansible/roles/ssd_wear_check` runs
`smartctl -a -j` against the real device and `ansible/roles/pve_power` exports
`smart_nvme_percentage_used`, `smart_nvme_available_spare_percent` and
`smart_nvme_media_errors` through node_exporter's textfile collector, feeding
`NVMeWearWarning` / `NVMeWearCritical` in
`kubernetes/system/monitoring/hardware-temp-alerts.yml`. Running Scrutiny on
`pve-mgmt-01` instead would duplicate that with a second dashboard for the same
disk.

The honest state of that replacement is recorded in `docs/STEADY-STATE.md`: the
host-level metrics pipeline is blocked by the unapplied
`fwd_04a_srv_monitoring` MikroTik/Terraform state gap, so the NVMe wear alerts
exist as code but are not live-firing. That gap is the real remaining work, it is
gated on the `terraform-apply` required-reviewer check, and it also blocks the
host-level I/O metrics that would settle the NFS stall question in ADR-047. Removing
Scrutiny does not make that worse; it stops a non-functional stack from reading as
disk-health coverage.

## Decision

Remove the Scrutiny stack: all eight objects the Application tracked (both PVCs,
both Services, the DaemonSet, the Deployment, the StatefulSet, the ExternalSecret),
plus the IngressRoute and the `.trivyignore` rules that pointed at the deleted
manifest. The `apps` Application itself is generated by the
`kubernetes/apps/*` ApplicationSet directory generator, so deleting the directory
makes ArgoCD drop the Application and prune everything it owned — including the
`scrutiny-secrets` Secret, which the ExternalSecret owns via `ownerReferences`.
Keep the host-side `smart_nvme_*` path as the single source of truth for disk wear.

An inert service is worse than an absent one. This one carried `hostPID` and
`CAP_SYS_RAWIO` on every node, an Authelia-gated public hostname, and two NFS PVCs,
and it had produced nothing since day one while appearing in `HOMELAB-AUDIT.md` as
"✅ Deployed". That is the same class of failure as the ArgoCD include-glob gap in
[PR #819](https://github.com/dwoitzik/homelab-infrastructure/pull/819): a status
line that was true about the manifest and false about the system.

## Consequences

- `scrutiny.woitzik.dev` stops serving. It does **not** stop resolving: DNS for this
  zone is a `*.woitzik.dev` wildcard (ADR-033), so the name keeps pointing at the
  tunnel and Traefik answers 404 once the IngressRoute is gone. The bookmarks pointed
  at a page with no data on it since 2026-07-20; they now point at a 404.
- Disk wear coverage is now entirely dependent on the host-side role, which is
  blocked on `fwd_04a_srv_monitoring`. Until that is applied, there is no *firing*
  SMART alert for the NVMe at all — which was already true, and is why this ADR
  pairs with a `STEADY-STATE.md` line rather than treating the removal as a fix.
- The `apps` namespace stays audit/warn-only for PodSecurity because kube-bench
  still needs `hostPID`. The comment naming Scrutiny as a second justification is
  corrected.
- Recovery is a `git revert` plus the PVC archives, which are NFS-backed and outlive
  the pod that produced them. The pre-removal archives are 44 KiB (InfluxDB: bolt
  file, sqlite and WAL) and 338 bytes (config, effectively empty) and contain no SMART
  history that was not already absent.

## Follow-up

`fwd_04a_srv_monitoring` needs a Terraform state import against the MikroTik, which
requires the `terraform-apply` required-reviewer gate — a human click, not something
an agent can route around. That single unblock restores NVMe wear alerts, host
power and thermal metrics, and the I/O data needed to close ADR-047.
